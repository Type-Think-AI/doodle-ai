# Doodle AI — SaaS Architecture

> **Status:** target architecture with the Phase 6 platform-credit generation path implemented. Persistence and billing details below include planned follow-up work.
> **Prerequisite:** [tech-stack.md](./tech-stack.md) — D1 + Drizzle + Better Auth + Stripe.
> **Companions:** [roadmap.md](./roadmap.md) · [mobile-strategy.md](./mobile-strategy.md)

## 1. Shape of the system

```
  Browser (Astro pages + src/scripts/app/*)          Mobile (Expo, later)
        │  cookie session                                  │  bearer token
        └──────────────────┬───────────────────────────────┘
                           ▼
              Astro SSR on Cloudflare Worker
              /api/v1/*  —  one API, two clients
                           │
        ┌──────────────────┼───────────────────┬──────────────────┐
        ▼                  ▼                   ▼                  ▼
      D1                  KV              PicX Studio          Stripe
  users, credits,    session cache,     assets + image      checkout +
  threads, ledger    rate limits        generation          webhooks
                                        (platform key)
```

The Worker is the only thing that holds secrets. `PICX_API_KEY` and `OPENROUTER_API_KEY` are `wrangler secret` values, never sent to a client. This is the whole point of the migration.

## 2. Schema

Drizzle, SQLite dialect, in `src/db/schema/`. Split into three files matching the three groups below.

### 2a. Better Auth owned — `src/db/schema/auth.ts`

Generated by the Better Auth CLI (`npx @better-auth/cli generate`). **Do not hand-edit.** Regenerate when Better Auth's schema version changes.

`user`, `session`, `account`, `verification` — plus whatever plugins we enable add.

Everything else foreign-keys to `user.id`. Because Better Auth's tables live in *our* D1 database, these are real foreign keys with real cascade behaviour, not a cross-service reference we have to reconcile.

### 2b. Billing — `src/db/schema/billing.ts`

// The append-only source of truth. Never UPDATE, never DELETE.
creditLedger = sqliteTable("credit_ledger", {
  id:             text("id").primaryKey(),                  // uuid
  userId:         text("user_id").notNull().references(() => user.id, { onDelete: "cascade" }),
  delta:          integer("delta").notNull(),               // +grant/purchase/refund, -spend
  reason:         text("reason").notNull(),                 // 'signup_grant' | 'purchase' | 'subscription_grant'
                                                            // | 'generation' | 'refund' | 'admin_adjustment'
  refId:          text("ref_id"),                           // generation.id, purchase.id, stripe event id
  idempotencyKey: text("idempotency_key").notNull().unique(),
  balanceAfter:   integer("balance_after").notNull(),       // snapshot, for audit + cheap reconciliation
  createdAt:      integer("created_at", { mode: "timestamp_ms" }).notNull(),
}, (t) => [ index("ledger_user_created_idx").on(t.userId, t.createdAt) ]);

// Denormalized running total. A cache of SUM(credit_ledger.delta), never
// authoritative — rebuildable from the ledger at any time.
creditBalance = sqliteTable("credit_balance", {
  userId:    text("user_id").primaryKey().references(() => user.id, { onDelete: "cascade" }),

## 3. The credit ledger

This is the part that deserves the most care, because it's the part where a bug costs money.

### Principles

**The ledger is append-only and authoritative.** Business logic never `UPDATE`s a balance. It appends a signed `delta` row. `credit_balance` is a cache written in the same transaction; if it ever disagrees with `SUM(delta)`, the ledger wins and the cache gets rebuilt.

**Every write carries an idempotency key**, `UNIQUE` at the database level. A retried Stripe webhook, a double-clicked buy button, or a client retrying a dropped generation request all produce the *same* key, so the second insert fails on the constraint and is caught and treated as success. Key construction:

| Event | Idempotency key |
|---|---|
| Signup grant | `signup:{userId}` |
| Purchase | `stripe:{eventId}` |
| Subscription monthly grant | `sub:{subscriptionId}:{periodStart}` |
| Generation spend | `gen:{generationId}` |
| Generation refund | `refund:{generationId}` |

Note the subscription key includes the period, so each month grants exactly once even if the webhook fires repeatedly.

### The spend path — debit first, refund on failure

```
1. Authenticate → userId
2. Resolve cost from the skill id (see pricing below)
3. BEGIN
     SELECT balance FROM credit_balance WHERE user_id = ?
     IF balance < cost → ROLLBACK, return 402 insufficient_credits
     INSERT generation (status='pending')
     INSERT credit_ledger (delta = -cost, reason='generation',
                           ref_id = generationId, idempotency_key = 'gen:'||generationId,
                           balance_after = balance - cost)
     UPDATE credit_balance SET balance = balance - cost
   COMMIT
4. Call PicX  ← the slow, failure-prone part, deliberately outside the transaction
5a. Success → UPDATE generation SET status='ok', output_url=?, completed_at=?
5b. Failure → INSERT credit_ledger (delta = +cost, reason='refund',
                idempotency_key = 'refund:'||generationId)
              UPDATE credit_balance SET balance = balance + cost
              UPDATE generation SET status='refunded', error_code=?
```

**Debit before, not after.** Charging after a successful generation means a user with 1 credit can fire twenty concurrent requests and get twenty images. Debiting first makes the balance the concurrency control.

**Why this is safe on D1.** The read-then-write in step 3 is a classic lost-update race: two concurrent requests both read balance 1, both write balance 0, and the user spends two credits' worth having paid for one. Postgres needs `SELECT ... FOR UPDATE` or `SERIALIZABLE` to prevent it. **D1 serializes all writes on a single thread**, so within a transaction the interleaving simply cannot occur. This is the concrete cash value of the tech-stack recommendation.

**If we take the Neon escape hatch, this changes.** Step 3 must become `SELECT ... FOR UPDATE` on the `credit_balance` row, or the transaction must run at `SERIALIZABLE` with retry-on-serialization-failure. Anyone doing that migration must read this section first — it is the single behavioural difference that a mechanical dialect swap will not catch.

### Failure modes

| Failure | Consequence | Handling |
|---|---|---|
| Worker killed between step 3 and step 4 | Credit debited, no generation | `generation` is left `pending`. Sweeper refunds anything `pending` for >10 min. |
| Worker killed during step 5b | Credit not refunded | Same sweeper catches it — the refund is idempotent, so re-running is safe. |
| PicX succeeds but response is lost | Credit spent, image orphaned on CDN | Acceptable. Do not auto-refund on timeout without confirming with PicX, or a slow-but-successful generation gets refunded *and* delivered. |
| Stripe webhook retried | Would double-credit | `webhook_event` primary key + the `stripe:{eventId}` idempotency key — two independent guards. |
| Client retries a generation request | Would double-charge | Client sends a request-scoped idempotency key; server reuses the same `generationId`. |

**Reconciliation job** (Cron Trigger, hourly):
1. Refund `generation` rows stuck `pending` for >10 minutes.
2. Assert `credit_balance.balance == SUM(credit_ledger.delta)` per user; log and repair mismatches from the ledger.
3. Alert on any negative balance — that means a guard failed somewhere.

### Pricing

Credit cost per skill lives next to the existing generation config in `src/lib/doodle-constants.ts`, keyed by `GENERATION_MODES` (`normal`, `collage`, `full-body`, `surprise`, `stickers`, `mood-captions`, `gift`). Multi-image skills like `stickers` should cost more. Resolve cost **server-side from the skill id** — never trust a client-supplied cost.

New accounts get a starter grant (`reason='signup_grant'`). Size it against PicX unit cost, not signup volume — see the cost model in [tech-stack.md](./tech-stack.md#5-cost-model).

## 4. API surface

Everything under `/api/v1/*`. JSON in, JSON out. **Both cookie sessions and `Authorization: Bearer` are accepted from day one** — that single decision is what lets the mobile app reuse this API with zero new endpoints.

| Method | Route | Auth | Notes |
|---|---|---|---|
| `*` | `/api/auth/*` | — | Better Auth handler (sign-up, sign-in, OAuth callbacks, refresh) |
| GET | `/api/v1/me` | ✔ | Profile + **credit balance** + subscription status. The client never computes a balance. |
| GET | `/api/v1/credits/packs` | — | Purchasable packs |
| GET | `/api/v1/credits/ledger` | ✔ | Paginated transaction history |
| POST | `/api/v1/credits/checkout` | ✔ | → Stripe Checkout session URL |
| POST | `/api/v1/webhooks/stripe` | sig | Signature-verified. **Not** session-authed. |
| GET/POST | `/api/v1/threads` | ✔ | List / create |
| GET/PATCH/DELETE | `/api/v1/threads/:id` | ✔ | Ownership-checked |
| GET | `/api/v1/threads/:id/messages` | ✔ | Paginated |
| POST | `/api/v1/upload` | ✔ | Replaces `src/pages/api/upload.ts`. Session-authenticated; the server uses the platform key. |
| POST | `/api/v1/chat` | ✔ | NDJSON stream. Same event shape as today (`text` / `image` / `done` / `error`) plus a new `credits` event so the UI can update the balance live. |
| GET | `/api/v1/generations` | ✔ | History |
| GET/POST/DELETE | `/api/v1/moodboard` | ✔ | |
| GET/POST/PATCH/DELETE | `/api/v1/characters` | ✔ | |
| POST | `/api/v1/import` | ✔ | One-time localStorage → server migration (Phase 3) |

**Error contract** — uniform, so both clients handle it identically:

```json
{ "error": { "code": "insufficient_credits", "message": "You need 2 credits.", "details": { "required": 2, "balance": 0 } } }
```

Codes: `unauthenticated` (401), `insufficient_credits` (402), `forbidden` (403), `not_found` (404), `rate_limited` (429), `upstream_error` (502). The existing habit in `src/pages/api/chat.ts` of logging real errors server-side and returning a generic message to the user is correct — keep it.

## 5. What changes in existing code

Described as patterns, not an exhaustive file list.

**The client never receives a provider credential.** Chat and upload requests are session-authenticated and contain no provider-key field. The old browser storage constant and legacy unmetered generation endpoint are removed.

**The agent tool reads the platform key.** `src/mastra/tools/generate-doodle.ts` receives the server-owned key through request context, requires an authenticated user and database handle, debits credits before PicX, and refunds failed generations. Exhausted balances return `insufficient-credits`.

**`/api/chat` requires a session and streams metered work.** The auth check and credit reservation happen before `agent.stream()`. The NDJSON contract survives intact, including `credits` events after successful generations.

**Each `localStorage` store gains a server-backed sibling.** `chat-store.ts`, `moodboard.ts` and `character-store.ts` keep their exported function signatures but route to `/api/v1/*` when signed in, `localStorage` when not. Keeping the signatures stable means the calling pages barely change. A one-time "import your local data" prompt on first sign-in POSTs the local blobs to `/api/v1/import` so existing users lose nothing.

**`/settings` is credential-free.** It explains the account-and-credit model and retains only appearance and visual-style preferences; billing and usage history remain planned follow-up surfaces.

**`wrangler.json` gains bindings.** `d1_databases`, `kv_namespaces`, a rate-limiting binding, and secrets (`PICX_API_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `BETTER_AUTH_SECRET`). Watch that no new dependency breaks the `vite.ssr.external` workaround in `astro.config.mjs` — verify with `pnpm check` after each addition.

## 6. Migrations

`drizzle.config.ts` targets the SQLite dialect with `driver: "d1-http"`. Workflow:

```bash
pnpm drizzle-kit generate            # schema diff → migrations/NNNN_name.sql
wrangler d1 migrations apply doodleai --local     # dev
wrangler d1 migrations apply doodleai --remote    # prod
```

Migration files are committed and forward-only — no down-migrations. To reverse, write a new forward migration. **Never edit an applied migration.**

Rules for a live database: additive changes only where possible; new columns nullable or defaulted; renames done as add → backfill → dual-write → drop across separate deploys. D1's 30-day Time Travel is the safety net for a bad migration, but it restores the *whole* database — treat it as disaster recovery, not routine rollback.
